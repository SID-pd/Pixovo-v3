# Stage 1.1 — Session continuity & chunked ingest

**Milestone 1 · 2–3 days · `[BLOCKER for all other stages]`**

---

## 1. Objective

Make it possible to upload 1,000 photos at all, under one stable session, resumably. Today a 1,000-photo upload is a single ~8 GB HTTP request that cannot complete, and the only fix — chunking — is blocked by a second defect that mints a fresh session per request. These two are one indivisible piece of work.

---

## 2. Current state

### 2.1 The upload is one monolithic request

[`client_downsampler.js:151`](../../frontend/src/utils/client_downsampler.js) `buildDualPayload()` builds a single `FormData` containing every thumbnail, **every full-resolution original**, and the full metadata array:

```js
processedPhotos.forEach((photo) => {
  formData.append('thumbnails', photo.thumbnail_blob, `${photo.photo_id}_thumb.jpg`);
  formData.append('originals', photo.original_file, `${photo.photo_id}_orig_${photo.filename}`);  // ← 8 MB each
  metadataArray.push({ ... });
});
formData.append('metadata_json', JSON.stringify(metadataArray));
```

[`App.jsx:144`](../../frontend/src/App.jsx) POSTs it whole:

```js
const res = await fetch('/api/photobook/ingest', { method: 'POST', body: formData });
```

At 1,000 photos × ~8 MB that is a **~8 GB single multipart POST**. It exhausts browser memory during serialisation and never reaches the network.

> `MVP_REPORT.md` §2.3 claims uploads are chunked in batches of 50. They are not. There is no chunking anywhere in the upload path. The only `chunk` in `client_downsampler.js` is the *downsampling* concurrency loop at line 123, which is unrelated to network transfer.

### 2.2 Every request mints a new session

[`main.py:138`](../../backend/app/main.py):

```python
async def ingest_photobook_dual_payload(thumbnails=..., originals=..., metadata_json=...):
    session_id = f"sess_{uuid.uuid4().hex[:8]}"   # ← generated per request
```

The endpoint accepts **no** `session_id` parameter. Chunking this endpoint as-is produces one orphaned session per chunk; only the first survives in the client's local `lastSessionId`, and the other 950 photos become unreachable.

### 2.3 The session ID does not survive a refresh

In [`App.jsx`](../../frontend/src/App.jsx) `handlePhotosUploaded`, the returned `session_id` is read from `data.session_id` and used only for a console log. It is never lifted into React state or storage. A refresh mid-upload orphans everything queued in IndexedDB.

### 2.4 Originals bypass session scoping entirely

[`main.py:652`](../../backend/app/main.py) `/api/upload-originals` takes `photo_id` as a query parameter and no session:

```python
orig_filename = f"{photo_id}_orig{file_ext}"
orig_path = UPLOADS_ORIGINALS_DIR / orig_filename        # ← flat, no session dir
```

But ingest writes originals to `UPLOADS_ORIGINALS_DIR / session_id / ...`. **The two paths disagree**, and `mark_original_synced()` overwrites the session-scoped `original_url` with the flat one — a latent PDF-export failure.

---

## 3. Target state

- An explicit session is created **before** any upload begins and returned to the client.
- Thumbnails + metadata upload in chunks of 25–50 under that one session ID.
- Chunks are idempotent: a retried chunk cannot double-insert.
- The session token survives a page refresh.
- All storage paths are session-scoped and consistent.
- Originals leave the ingest payload entirely (implemented in [Stage 1.3](M1-1.3-storage-offload.md); this stage only removes them from `buildDualPayload`).

### Task 4 — Chunk the client upload

Split `buildDualPayload` into a thumbnails-only chunk builder in [`client_downsampler.js`](../../frontend/src/utils/client_downsampler.js):

```js
/**
 * Build ONE chunk payload: thumbnails + metadata only.
 * Originals are uploaded separately by the background sync (Stage 1.3).
 */
buildChunkPayload(processedPhotos, sessionId, chunkIndex, chunkCount) {
  const formData = new FormData();
  const metadataArray = [];

  processedPhotos.forEach((photo) => {
    if (photo.thumbnail_blob) {
      formData.append('thumbnails', photo.thumbnail_blob, `${photo.photo_id}_thumb.jpg`);
    }
    metadataArray.push({
      photo_id: photo.photo_id,
      filename: photo.filename,
      original_size_bytes: photo.original_size_bytes,
      original_width: photo.original_width,
      original_height: photo.original_height,
      aspect_ratio: photo.aspect_ratio,
      orientation: photo.orientation,
      timestamp: photo.timestamp,
      timestamp_epoch: Math.floor(new Date(photo.timestamp).getTime() / 1000),  // Stage 1.2 needs this
      thumbnail_size_bytes: photo.thumbnail_size_bytes,
    });
  });

  formData.append('session_id', sessionId);
  formData.append('chunk_index', String(chunkIndex));
  formData.append('chunk_count', String(chunkCount));
  formData.append('metadata_json', JSON.stringify(metadataArray));
  return formData;
}

static chunk(items, size = 40) {
  const out = [];
  for (let i = 0; i < items.length; i += size) out.push(items.slice(i, i + size));
  return out;
}
```

Keep `buildDualPayload` as a thin deprecated wrapper for one release, or delete it outright — it has exactly one caller ([`PhotoUploader.jsx:66`](../../frontend/src/components/PhotoUploader.jsx)).

> `timestamp_epoch` is added here deliberately. [Stage 1.2](M1-1.2-data-contract.md) needs it and the client is the only place the true capture time is known cheaply. Adding it now avoids touching this function twice.

### Task 5 — Sequential chunk upload with retry

Replace the single `fetch` in [`App.jsx`](../../frontend/src/App.jsx) `handlePhotosUploaded`:

```js
const CHUNK_SIZE = 40;
const MAX_RETRIES = 3;

const uploadChunkWithRetry = async (formData, attempt = 0) => {
  try {
    const res = await fetch('/api/photobook/ingest', { method: 'POST', body: formData });
    if (res.ok) return await res.json();
    if (res.status >= 400 && res.status < 500) {
      throw new Error((await res.json().catch(() => ({}))).detail || `Rejected (${res.status})`);
    }
    throw new Error(`Server error ${res.status}`);
  } catch (err) {
    if (attempt < MAX_RETRIES) {
      await new Promise(r => setTimeout(r, 2 ** attempt * 1000));   // 1s, 2s, 4s
      return uploadChunkWithRetry(formData, attempt + 1);
    }
    throw err;
  }
};

// 1. Open the session BEFORE uploading anything
const sessionRes = await fetch('/api/sessions', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ expected_photo_count: processedPhotos.length }),
});
const { session_id } = await sessionRes.json();
setSessionId(session_id);
sessionStorage.setItem('pixovo_session_id', session_id);

// 2. Upload thumbnail chunks sequentially under that session
const chunks = PixovoClientDownsampler.chunk(processedPhotos, CHUNK_SIZE);
const allPhotos = [];
for (let i = 0; i < chunks.length; i++) {
  const payload = downsampler.buildChunkPayload(chunks[i], session_id, i, chunks.length);
  const data = await uploadChunkWithRetry(payload);
  allPhotos.push(...(data.photos || []));
  setIngestProgress({ done: i + 1, total: chunks.length, survived: data.session_survived });
}
uploadedPhotosRef.current = allPhotos;
setUploadedPhotos(allPhotos);
setIsPhotoUploadComplete(true);
```

**Sequential, not parallel, on purpose.** Each chunk triggers CPU-bound filtering server-side; firing 25 chunks concurrently from 20 users is 500 simultaneous filter batches. Sequential per user, concurrent across users, is the correct shape — and it makes `chunk_index` meaningful for resume.

### Task 6 — Idempotent chunks

`save_photos_batch()` ([`session_store.py:115`](../../backend/app/db/session_store.py)) already uses `INSERT OR REPLACE INTO photos` keyed on the client-minted `photo_id`, so a replayed chunk overwrites rather than duplicates. Two things must hold for that to be true in practice:

1. **The photo_id must be stable across retries.** It is — minted once in `processSinglePhoto()` ([`client_downsampler.js:29`](../../frontend/src/utils/client_downsampler.js)) and carried in the metadata.
2. **Session counters must not double-count.** Derive them with `SELECT COUNT(*) FROM photos WHERE session_id = ?` after each batch insert rather than incrementing a running total, so a replay converges instead of inflating.

Also fix the ID-resolution logic while in this code. [`main.py:216`](../../backend/app/main.py) builds a `metadata_map` dict and then ignores it, scanning `metadata_list` linearly per survived photo and falling back to stripping `_thumb.jpg` off filenames. Use the dict, and make the client-minted `photo_id` the single join key end to end:

```python
# thumbnails are uploaded as f"{photo_id}_thumb.jpg" — parse the ID back out directly
p_id = Path(item["filename"]).stem.replace("_thumb", "")
meta = metadata_map.get(p_id)
if not meta:
    logger.warning(f"[Ingest] No metadata for {p_id}; skipping")
    continue
```

## 6. Test plan

**Unit (backend)**
- `create_session` → `get_session` round-trips; unknown ID returns `None`.
- Ingest with an unknown `session_id` → 404; expired → 410.
- Replaying an identical chunk twice → photo count unchanged (idempotency).
- ID resolution: a thumbnail named `px_abc123_xyz_thumb.jpg` resolves to metadata key `px_abc123_xyz`.

**Unit (frontend)**
- `chunk(items, 40)` on 1,000 items → 25 chunks, last one 40, no loss.
- `buildChunkPayload` emits `thumbnails`, `metadata_json`, `session_id`, `chunk_index`, `chunk_count` — and **no** `originals` key.
- `uploadChunkWithRetry` retries on 500, does **not** retry on 400.

**Integration**
- 1,000 synthetic photos → exactly one `session_id`, ~25 ingest requests, all photos under that session.
- Kill the browser at chunk 15, reload, resume → no duplicates, no loss.
- Two concurrent sessions → `get_session_photos()` returns disjoint sets.

## 7. Exit criteria

- [ ] 1,000 photos ingest under **one** session ID.
- [ ] No single ingest request exceeds **5 MB**.
- [ ] A killed/resumed upload produces no duplicates and loses no photos.
- [ ] Two concurrent sessions never see each other's photos.
- [ ] `session_id` survives a page refresh.
- [ ] `grep -n "uuid4().hex\[:8\]" backend/app/main.py` returns nothing for sessions.
- [ ] Original files land in `/uploads/originals/{session_id}/` from **both** write paths.

## 8. Risks & rollback

| Risk | Mitigation |
|---|---|
| Chunked upload is slower end-to-end than one request | Expected and acceptable — one request currently never completes. Measure in 1.7; raise `CHUNK_SIZE` if per-request overhead dominates. |
| Partial session left when a user abandons mid-upload | `status='ingesting'` plus `last_accessed_at`; the Milestone 3 retention sweep reaps them. Harmless meanwhile. |
| `sessionStorage` unavailable (private mode) | Fall back to in-memory state; upload still works, refresh-resume does not. Wrap in try/catch. |
| Existing rows have `session_id = NULL` | Dev-only data. Delete `backend/pixovo_session.db` and let `init_db()` recreate it — the file is currently committed and should stop being tracked regardless. |

**Rollback:** all changes are additive except the ingest signature. Revert the `App.jsx` upload loop and the `client_downsampler` payload builder together; the backend accepting `session_id` is backward-compatible if defaulted, so revert the frontend first and the backend second.
