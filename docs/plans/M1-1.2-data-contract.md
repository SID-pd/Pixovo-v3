# Stage 1.2 — Restore the data contract

**Milestone 1 · 3–4 days · Depends on [1.1](M1-1.1-session-continuity.md) · `[BLOCKER for 1.5]`**

---

## 1. Objective

Reconnect the filter engine to the layout engine. Every signal the filter engine computes — hero score, perceptual hashes, capture time, GPS, blur, face count, dominant colours — is currently discarded at a single boundary, so clustering, chaptering and hero selection all run on null inputs. This is the highest-leverage change in the project: one boundary fix restores four downstream systems at once.

**This is the stage that delivers "exact outcome as we need."**

### Task 3 — Fall back to client EXIF for `timestamp_epoch`

The filter engine's `taken_at` comes from EXIF on the **thumbnail**, and the canvas downsample in `client_downsampler.js` strips EXIF. So `taken_at` will frequently be 0 or the file mtime.

[Stage 1.1 Task 4](M1-1.1-session-continuity.md) already adds `timestamp_epoch` to the client metadata from `file.lastModified`. Resolve with a clear precedence:

```python
ts = (
    float(item.get("taken_at") or 0)                    # 1. EXIF from the image itself
    or float(meta.get("timestamp_epoch") or 0)          # 2. client file.lastModified
    or 0.0                                              # 3. unknown
)
```

Log the distribution once per chunk — if most photos land on fallback 2, chaptering degrades to file-order and you want to know:

```python
exif_hits = sum(1 for i in survived_photos_list if i.get("taken_at"))
logger.info(f"[Ingest] Capture-time source: EXIF {exif_hits}/{len(survived_photos_list)}")
```

**Optional follow-on (recommended, ~0.5 day):** parse EXIF client-side from the *original* file before downsampling, using a small `DataView` reader over the JPEG APP1 segment — no dependency needed. Read `DateTimeOriginal` and `GPSLatitude`/`GPSLongitude`. This is the only way to get true capture time and GPS, and without GPS the 5-km chapter rule can never fire. Do it in the worker introduced in [2.1](M2-2.1-worker-downsampling.md) so it costs no main-thread time.

### Task 5 — Persist and retrieve the new columns

[`session_store.py`](../../backend/app/db/session_store.py) — add columns to the `photos` table:

```python
conn.execute("""
    CREATE TABLE IF NOT EXISTS photos (
        ... existing ...,
        timestamp_epoch REAL DEFAULT 0,
        latitude REAL, longitude REAL,

        is_event_cover_hero INTEGER DEFAULT 0,
```

`CREATE TABLE IF NOT EXISTS` will **not** add columns to an existing table. Either delete `backend/pixovo_session.db` (dev-only data, and it should stop being git-tracked regardless) or add an idempotent migration:

```python
def _ensure_columns(conn):
    existing = {r["name"] for r in conn.execute("PRAGMA table_info(photos)")}
    for col, ddl in [
        ("timestamp_epoch", "REAL DEFAULT 0"), ("latitude", "REAL"), ("longitude", "REAL"),
        ("hero_score", "REAL DEFAULT 0"), ("layout_role", "TEXT DEFAULT 'SUPPORT'"),
        ("is_event_cover_hero", "INTEGER DEFAULT 0"),
        ("tenengrad_score", "REAL"), ("contrast_score", "REAL"),
    ]:
        if col not in existing:
            conn.execute(f"ALTER TABLE photos ADD COLUMN {col} {ddl}")
```

Then update **all three** read paths — `get_photo()` ([:156](../../backend/app/db/session_store.py)), `get_photos()` ([:187](../../backend/app/db/session_store.py)), `get_session_photos()` ([:229](../../backend/app/db/session_store.py)) — and the `save_photos_batch()` INSERT ([:115](../../backend/app/db/session_store.py)).

> These three methods each hand-build an identical `PhotoMeta(...)` from a row — ~20 duplicated lines × 3, and adding 8 fields makes it ~28 × 3. **Extract one `_row_to_photo_meta(row)` helper first.** It is 15 minutes and it prevents the classic bug where you update two of three read paths and spend an afternoon on why photos are correct via one endpoint and null via another.

## 8. Risks & rollback

| Risk | Mitigation |
|---|---|
| Restored clustering produces *worse*-looking albums than array order | Genuinely possible — the algorithms have never run on real input and are therefore untuned. Budget a day for threshold tuning against the fixture corpus. This is real work being surfaced, not created. |
| EXIF is absent after canvas downsampling | Precedence chain falls back to `file.lastModified`; log the hit rate. Client-side EXIF parsing (Task 3 follow-on) is the durable fix. |
| Existing DB rows lack the new columns | Idempotent `ALTER TABLE` migration, or delete the dev DB. |
| Colour extraction slows ingest | Run it inside the filter worker on the already-decoded thumbnail — near-zero marginal cost. Measure in 1.7. |
| Only 2 of 3 read paths updated | The `_row_to_photo_meta()` extraction in Task 5 structurally prevents this. Do it first. |

**Rollback:** the schema additions are all optional-with-defaults, so old code ignores them safely. To revert behaviour without reverting the schema, restore the original `PhotoMeta(...)` constructor in `main.py` — one hunk.

## 8b. Corrections found during implementation

Two things in the plan above were wrong. Recorded here rather than silently edited, because both affect later stages.

**1. `layout_role` values were guessed.** The plan said `HERO_SPREAD | FEATURE | SUPPORT`. `compute_hero_score()` actually emits:

| Value | Condition |
|---|---|
| `DOUBLE_PAGE_HERO` | `hero_score >= 75` **and** `aspect_ratio >= 1.35` |
| `FULL_PAGE_HERO` | `hero_score >= 62` |
| `STANDARD_FRAME` | otherwise |

Stage 1.5 should read these directly — `DOUBLE_PAGE_HERO` is already a ready-made cover-candidate signal.

**2. `taken_at` cannot be trusted unconditionally — this was a real bug in the plan.** Task 3's precedence put `item["taken_at"]` first. But `extract_5_signal_metadata()` sets `date_source` to one of `exif_datetime`, `filename_regex`, `mtime`, or `current_time`, and it reads the **thumbnail** — a temp file the server wrote seconds earlier. So the `mtime` fallback returns *"now"* for every photo in a chunk, giving every photo an identical timestamp and silently disabling both the 45-minute chapter rule and the filter engine's own event clustering.

The first implementation reported `capture-time EXIF 9/9` while producing 1 chapter from 3 deliberately time-separated clusters. Two changes fixed it:

- **Gate on `date_source`:** only prefer `taken_at` when it came from `exif_datetime` or `filename_regex`; otherwise use the client's `timestamp_epoch`.
- **Stamp the thumbnail's mtime** with the client capture time immediately after writing it (`os.utime`), so the filter engine's *internal* `cluster_events()` — which reads `taken_at` directly and which ingest cannot influence otherwise — also gets real times.

After both: `3 Story Chapters | splits: time=2 gps=0 cap=0`.

**Known limitation to carry forward:** filtering runs **per ingest chunk**, so burst dedupe, event clustering and `is_event_cover_hero` are all chunk-local. Cross-chunk duplicates are not caught, and a 1,000-photo session produces one "event hero" per chunk-event. `hero_score` is computed per photo independently and is therefore globally comparable — **Stage 1.5 must rank on `hero_score` across the whole session and treat `is_event_cover_hero` as advisory only.** A session-level dedupe re-pass belongs in Stage 1.7 if the load test shows it matters.

## 9. Why this stage is worth 3–4 days

It is the difference between a photobook generator and a photo-grid generator. Everything the product claims to do — story chapters, visual grouping, hero placement — is implemented, tested by its authors, and currently unreachable. No new algorithms are written here. The work is plumbing, and the payoff is the entire differentiated feature set switching on at once.
