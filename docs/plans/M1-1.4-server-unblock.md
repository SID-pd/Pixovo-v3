# Stage 1.4 — Unblock the server

**Milestone 1 · 2 days · Depends on [1.3](M1-1.3-storage-offload.md)**

---

## 1. Objective

Make the server able to serve 20 concurrent sessions. Four separate defects each independently stall it: full-resolution decoding on the event loop, the layout solver running on the event loop, nested thread pools oversubscribing the CPU, and unbounded in-memory caches. None is hard to fix; all are invisible at a demo scale of 20 photos and fatal at 20,000.

---

## 2. Current state

### Defect A — Full-resolution decode on the event loop

Ingest step 5b ([`main.py:186`](../../backend/app/main.py)) runs inside the `async def` handler, **not** in the worker pool:

```python
for item in filter_result.get("survived_photos", []):
    matching_orig_path = None
    for orig_name, orig_path in saved_orig_map.items():      # O(survivors × originals)
        if any(k in orig_name for k in [item.get("photo_id",""), item.get("filename","")] if k):
            matching_orig_path = orig_path
            break
    if matching_orig_path:
        orig_bgr = cv2.imread(matching_orig_path)            # ← 100-300ms, blocking, full-res
        ...detectAndDecodeMulti(orig_bgr)
```

`cv2.imread` on an 8 MB JPEG takes 100–300 ms. Across a 40-photo chunk that is **4–12 seconds during which the entire server serves nobody** — `asyncio` cannot switch tasks out of synchronous C code. Twenty concurrent sessions is total stall.

The nested loop is additionally O(n²) in filenames.

### Defect B — The layout solver also runs on the event loop

[`main.py:748`](../../backend/app/main.py), inside `process_async_job`:

```python
ai_batch = generate_story_theme_batch(user_prompt, total_photos=len(photos))   # sync
...
variations = generate_photobook_variations_engine(photos, ai_batch)           # sync, CPU-heavy
```

Neither is awaited or offloaded. `generate_photobook_variations_engine` runs the DSA solver over every spread for **three variations**; at 1,000 photos that is hundreds of `build_dsa_spread_pair` calls with pHash comparisons — seconds of pure CPU on the event loop.

`process_async_job` is dispatched via `BackgroundTasks` ([`main.py:799`](../../backend/app/main.py)), which runs **in the same event loop** as request handling. The `asyncio.Semaphore(4)` limits how many run concurrently but does nothing about blocking: 4 blocked coroutines block everything.

This is why job progress jumps in steps — the `await asyncio.sleep(0.1)` calls between stages are the only points the loop can breathe.

### Defect C — Nested thread pools

```python
# main.py:39
CPU_WORKER_POOL = ThreadPoolExecutor(max_workers=4)

# filter_engine.py:1003, inside run_phase1_filtering — called on a CPU_WORKER_POOL thread
max_workers = min(4, os.cpu_count() or 2)
for i in range(0, len(filepaths), chunk_size):        # chunk_size = 50
    with ThreadPoolExecutor(max_workers=max_workers) as executor:   # ← new pool per chunk
        ...
    gc.collect()
```

Three compounding problems:

1. **Oversubscription** — 4 outer × 4 inner = 16 CPU-bound threads on a typical 8-core machine, before OpenCV's own threading.
2. **`cv2.setNumThreads()` is never called** — OpenCV spawns `cpu_count` threads *per operation*, on each of those 16 threads.
3. **A pool is constructed and destroyed per 50-photo chunk** — thread creation churn plus a `gc.collect()` (a full stop-the-world pass) every 50 photos.

### Defect D — Unbounded caches

```python
# main.py:69-70
PHOTO_STORE: Dict[str, PhotoMeta] = {}
JOBS_STORE:  Dict[str, JobStatusResponse] = {}
```

Never evicted. At 20 × 1,000 that is 20,000 `PhotoMeta` objects retained for process lifetime, plus every job with its full `variations` payload — the largest object in the system. SQLite is already the source of truth behind both, with fallback paths already written ([`main.py:757`](../../backend/app/main.py), [`main.py:812`](../../backend/app/main.py)), so eviction is safe by construction.

## 3. Target state

The event loop never blocks more than ~50 ms. All CPU work runs in one correctly-sized pool. Caches are bounded. `/health` stays responsive under full load.

## 4. Tasks

### Task 1 — Delete the ingest QR loop

[Stage 1.3](M1-1.3-storage-offload.md) removes originals from ingest, so this loop has no input. **Delete [`main.py:186-204`](../../backend/app/main.py) entirely.**

If QR re-verification on originals is still wanted, move it to the background sync where the original actually arrives, run it in the worker pool, and only for photos the junk detector flagged as *suspected*:

```python
if photo.junk_suspected:
    loop = asyncio.get_running_loop()
    is_qr = await loop.run_in_executor(CPU_POOL, verify_qr_on_original, key)
    if is_qr:
        SessionStore.mark_rejected(photo_id, "Junk QR Code in Original")
```

Full-resolution QR decoding is not worth 300 ms per photo across the whole set — the 512px thumbnail already catches the overwhelming majority.

### Task 2 — Offload the job worker

```python
async def process_async_job(job_id: str, session_id: str, photo_ids: List[str], user_prompt: str):
    async with CONCURRENCY_SEMAPHORE:
        loop = asyncio.get_running_loop()
        try:
            await _update_job(job_id, 20, "Loading photos...")
            photos = await loop.run_in_executor(CPU_POOL, _load_photos, photo_ids)
            if not photos:
                await _fail_job(job_id, "No valid photos found for this session.")
                return

            await _update_job(job_id, 40, "Generating story themes...")
            ai_batch = await loop.run_in_executor(
                CPU_POOL, generate_story_theme_batch, user_prompt, len(photos))

            await _update_job(job_id, 60, "Solving layouts...")
            variations = await loop.run_in_executor(
                CPU_POOL, generate_photobook_variations_engine, photos, ai_batch)

            await _complete_job(job_id, variations)
        except Exception as e:
            logger.error(f"[JobWorker] {job_id} failed: {e}", exc_info=True)
            await _fail_job(job_id, str(e))
```

Delete the `await asyncio.sleep(0.1)` calls — they exist only to let the loop breathe between blocking sections, and `run_in_executor` makes them unnecessary.

`_load_photos` should prefer `SessionStore.get_session_photos(session_id)` (one indexed query) over `get_photos(photo_ids)` (chunked `IN` clauses) — see Task 6.

### Task 3 — One pool, correctly sized

[`config.py`](../../backend/app/config.py):

```python
import os, cv2

CPU_COUNT      = os.cpu_count() or 4
FILTER_WORKERS = int(os.environ.get("PIXOVO_FILTER_WORKERS", max(2, CPU_COUNT - 1)))
JOB_CONCURRENCY = int(os.environ.get("PIXOVO_JOB_CONCURRENCY", max(2, CPU_COUNT // 2)))

cv2.setNumThreads(1)   # we parallelise across photos; OpenCV must not also fan out per-op
```

Reserve one core for the event loop — a fully saturated pool starves request handling and the symptom looks like a network problem.

In [`main.py`](../../backend/app/main.py):
```python
CPU_POOL = ThreadPoolExecutor(max_workers=FILTER_WORKERS, thread_name_prefix="pixovo-cpu")
CONCURRENCY_SEMAPHORE = asyncio.Semaphore(JOB_CONCURRENCY)
```

In [`filter_engine.py:1001`](../../backend/app/engine/filter/filter_engine.py) — **delete the inner pool**. The function is already called on a pool thread; it should process its batch serially and let the caller parallelise:

```python
def run_phase1_filtering(self, filepaths: List[str]) -> Dict[str, Any]:
    scanned_photos = [
        self.process_single_photo(fp, f"p_{idx+1}")
        for idx, fp in enumerate(filepaths)
    ]
    # ... unchanged downstream logic ...
```

Then fan out **per photo** from the caller, which gives real parallelism across concurrent sessions rather than nested pools fighting each other:

```python
futures = [loop.run_in_executor(CPU_POOL, filter_engine.process_single_photo, fp, pid)
           for fp, pid in zip(thumb_paths, photo_ids)]
scanned = await asyncio.gather(*futures)
result  = filter_engine.finalise_batch(scanned)   # dedupe, cluster, hero — cheap, no I/O
```

This requires splitting `run_phase1_filtering` into `process_single_photo` (parallel, already exists) and `finalise_batch` (serial: the safeguard pass, burst dedupe, DBSCAN, hero ranking — currently lines 1017–1138). A clean split, and it makes both halves independently testable.

Also remove the per-chunk `gc.collect()`. A full collection every 50 photos is a stop-the-world pause; if memory pressure is real, fix the retention, not the symptom. Keep at most one `gc.collect()` at end-of-session.

### Task 4 — Threads vs processes: measure, don't argue

OpenCV releases the GIL for most operations, so threads *should* parallelise. But `process_single_photo` also calls PIL and `imagehash`, which largely do not. The right answer is not derivable by inspection.

Add an env switch and benchmark it in [Stage 1.7](M1-1.7-load-proof.md):

```python
POOL_KIND = os.environ.get("PIXOVO_POOL", "thread")   # thread | process
CPU_POOL = (ProcessPoolExecutor(max_workers=FILTER_WORKERS)
            if POOL_KIND == "process" else
            ThreadPoolExecutor(max_workers=FILTER_WORKERS))
```

`ProcessPoolExecutor` requires picklable arguments and returns — pass file paths and plain dicts, never `PhotoMeta` objects or the engine instance. `process_single_photo` already takes `(filepath, photo_id)` and returns a dict, so it is a candidate as written; the caveat is that `Phase1FilterEngine` holds loaded face-detector models, which must then load once per worker process. Budget ~2 s of extra startup per worker and use `initializer=` to warm them.

Decide by number: photos/sec/core at 1,000 photos.

### Task 5 — Bound the caches

```python
from cachetools import TTLCache

PHOTO_STORE = TTLCache(maxsize=int(os.environ.get("PIXOVO_PHOTO_CACHE", 8000)), ttl=3600)
JOBS_STORE  = TTLCache(maxsize=500, ttl=3600)
```

Add `cachetools>=5.3.0` to `requirements.txt`. Both already have SQLite fallbacks on miss, so a cache miss is correct, merely slower. Two details:

- `TTLCache` is **not thread-safe**; these are touched from pool threads. Guard with a `threading.Lock`, or keep all mutation on the event loop.
- Never let a cache miss become a 404. [`main.py:812`](../../backend/app/main.py) already falls back to `SessionStore.get_job()` — verify the same for photos on every read path.

### Task 6 — Query by session, not by ID list

`process_async_job` receives `photo_ids` and calls `get_photos(photo_ids)`, which chunks into `IN (...)` clauses of 500. With `session_id` available (Stage 1.1) and an index on `photos(session_id)` (Stage 1.1 Task 1), one query replaces it:

```python
photos = SessionStore.get_session_photos(session_id)
```

Also fix connection churn: `get_db_connection()` ([`session_store.py:15`](../../backend/app/db/session_store.py)) opens a new connection and runs **four PRAGMAs** on every call. Use a thread-local connection:

```python
_local = threading.local()

def get_db_connection() -> sqlite3.Connection:
    conn = getattr(_local, "conn", None)
    if conn is None:
        conn = sqlite3.connect(str(DB_PATH), check_same_thread=False, timeout=30.0)
        for pragma in ("journal_mode=WAL", "synchronous=NORMAL",
                       "busy_timeout=30000", "temp_store=MEMORY"):
            conn.execute(f"PRAGMA {pragma};")
        conn.row_factory = sqlite3.Row
        _local.conn = conn
    return conn
```

The `finally: conn.close()` in every method must then become a no-op — audit all call sites, since closing a shared connection breaks the next caller on that thread.

## 6. Test plan

**Event-loop responsiveness — the core test**

```python
async def test_event_loop_not_blocked_during_ingest():
    ingest = asyncio.create_task(post_ingest_chunk(40_photos))
    lags = []
    while not ingest.done():
        t0 = time.perf_counter()
        await client.get("/health")
        lags.append(time.perf_counter() - t0)
        await asyncio.sleep(0.05)
    assert max(lags) < 0.2, f"Event loop blocked {max(lags)*1000:.0f}ms"
```

Run the same against `/api/generate-async` for Defect B.

**Unit**
- `finalise_batch()` on a fixed scanned list produces identical output to the old `run_phase1_filtering` (behaviour-preserving refactor).
- `PHOTO_STORE` eviction: insert `maxsize + 100`, confirm size is capped and evicted IDs still resolve from SQLite.
- `get_db_connection()` returns the same object twice on one thread, different objects across threads.

**Load smoke (full test in [1.7](M1-1.7-load-proof.md))**
- 4 concurrent sessions × 200 photos: p99 `/health` < 200 ms.
- Thread count stays bounded — no growth per chunk.

## 8. Risks & rollback

| Risk | Mitigation |
|---|---|
| Splitting `run_phase1_filtering` changes filtering behaviour | Golden-output test on a fixed corpus before and after. The split is mechanical: parallel part vs serial part, no logic change. |
| `ProcessPoolExecutor` breaks on unpicklable state | Face-detector models must load per worker via `initializer=`. If it proves awkward, threads + `cv2.setNumThreads(1)` already fixes most oversubscription — processes are an optimisation, not a requirement. |
| Thread-local connections leak across a large pool | One connection per pool thread, pool is bounded, so connections are bounded. SQLite WAL supports concurrent readers. |
| `TTLCache` races under thread access | Guard with a lock or confine mutation to the event loop. Misses are correct-but-slower, so races degrade performance, not correctness. |
| Removing `gc.collect()` raises memory | Measure in 1.7. Retention and bounded caches are the real fix; a forced full GC every 50 photos is treating a symptom. |

**Rollback:** every change is behaviour-preserving except the QR-loop deletion (which loses full-res QR re-checking — an acceptable, documented trade). Pool sizing and cache bounds are env-configurable, so a bad value is a config change, not a redeploy.
