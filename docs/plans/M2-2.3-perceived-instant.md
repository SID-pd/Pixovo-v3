# Stage 2.3 — Perceived instant

**Milestone 2 · 3–4 days · Depends on [1.2](M1-1.2-data-contract.md), [2.2](M2-2.2-sse-progress.md)**

---

## 1. Objective

Make the app feel instant regardless of what the server is doing. The technique is not speed — it is never showing an empty state. The browser already holds every thumbnail it just generated, and the backend already computes every photo's dominant colours; both are currently unused for presentation.

---

## 2. Current state

### 2.1 The client throws away previews it already has

[`PhotoUploader.jsx:52`](../../frontend/src/components/PhotoUploader.jsx) builds `previewItems` with local object URLs and passes them up. [`App.jsx`](../../frontend/src/App.jsx) `handlePhotosUploaded` destructures `previewItems`… and never uses it. The UI waits for the server to return `data.photos` and then loads those thumbnails **back over HTTP** — images the browser already has in memory.

### 2.2 The upload step blanks immediately

`handlePhotosUploaded` calls `setStep('chat')` before ingestion begins. Photos vanish from view during the longest phase; the user has no confirmation anything is happening.

### 2.3 Covers pop in

`BookCarousel3D` renders `<img src={cover_image_url}>` with no reserved space and no placeholder. Three images load at unpredictable times, each shifting layout as it arrives.

### 2.4 `dominant_colors` is computed and unused

After [Stage 1.2](M1-1.2-data-contract.md), every `PhotoMeta` carries real dominant colours. Nothing renders them. This is exactly the data needed for blur-up placeholders — no extra computation, no extra request.

### 2.5 Spreads have no loading affordance

[`SpreadViewer.jsx`](../../frontend/src/components/SpreadViewer.jsx) virtualizes (visible + 2 buffer) but the `<img>` tags lack `width`/`height`, `loading`, and `decoding`, so each spread reflows as its photos arrive.

---

## 3. Target state

- Photos appear instantly from local blobs; server URLs swap in silently.
- Every image has reserved space and a colour placeholder — zero layout shift.
- Covers paint immediately as themed shapes, then cross-fade to photos.
- Progress reflects real work (from [2.2](M2-2.2-sse-progress.md)) and stays visible.

## 4. Tasks

### Task 1 — Optimistic local previews

Keep the local object URLs and render from them until the server confirms:

```js
// App.jsx — render from local blobs immediately, reconcile as chunks land
const [localPreviews, setLocalPreviews] = useState([]);   // { photo_id, previewUrl, aspect_ratio }
const [serverPhotos, setServerPhotos]   = useState({});   // photo_id -> PhotoMeta

const photos = useMemo(() => localPreviews.map(lp => {
  const server = serverPhotos[lp.photo_id];
  return {
    ...lp,
    url: server?.url || lp.previewUrl,      // server URL once known, local blob until then
    status: server ? (server.rejected ? 'rejected' : 'kept') : 'pending',
    dominant_colors: server?.dominant_colors,
  };
}), [localPreviews, serverPhotos]);
```

The `photo_id` is minted client-side ([`client_downsampler.js:29`](../../frontend/src/utils/client_downsampler.js)) and echoed by the server, so reconciliation is a dictionary lookup. **Perceived latency for the photo grid drops to zero.**

Free each local URL only once its server URL is in use:

```js
useEffect(() => {
  Object.keys(serverPhotos).forEach(id => {
    const lp = localPreviews.find(p => p.photo_id === id);
    if (lp?.previewUrl) { URL.revokeObjectURL(lp.previewUrl); lp.previewUrl = null; }
  });
}, [serverPhotos]);
```

### Task 2 — Keep photos visible during ingest

Instead of blanking on `setStep('chat')`, keep the grid as a compact strip above the theme prompt, with live per-photo state from ingest:

- **pending** — full colour, subtle shimmer
- **kept** — full colour, no badge (the default; don't decorate the normal case)
- **rejected** — dimmed to 40% with a one-word reason on hover (`blurry`, `duplicate`, `junk`)

This turns the longest phase into the most reassuring one: the user watches curation happen instead of staring at a spinner. It also makes the filter engine's decisions visible, which is a product feature in its own right — it is the thing the user would otherwise have done by hand.

### Task 3 — Colour placeholders everywhere

`frontend/src/components/PhotoFrame.jsx`:

```jsx
export default function PhotoFrame({ src, aspectRatio = 1.33, dominantColors, alt = '', className }) {
  const [loaded, setLoaded] = useState(false);
  const bg = dominantColors?.length
    ? `linear-gradient(135deg, ${dominantColors[0]}, ${dominantColors[1] || dominantColors[0]})`
    : 'var(--pixovo-skeleton, #E5E7EB)';

  return (
    <div className={className}
         style={{ position: 'relative', aspectRatio: String(aspectRatio),
                  background: bg, overflow: 'hidden' }}>
      {src && (
        <img src={src} alt={alt} loading="lazy" decoding="async"
             onLoad={() => setLoaded(true)}
             style={{ width: '100%', height: '100%', objectFit: 'cover',
                      opacity: loaded ? 1 : 0,
                      transition: 'opacity 220ms ease-out' }} />
      )}
    </div>
  );
}
```

Two things do the work: the wrapper's `aspectRatio` reserves exact space **before** the image loads (no layout shift), and the dominant-colour gradient means the pre-load state looks like the photo rather than like a grey box.

Use it in `PhotoUploader` grid, `SpreadViewer` slots, and `BookCarousel3D` covers. `aspect_ratio` and `dominant_colors` are already on every `PhotoMeta` after [Stage 1.2](M1-1.2-data-contract.md).

### Task 5 — Progressive spreads

In [`SpreadViewer.jsx`](../../frontend/src/components/SpreadViewer.jsx):

- Replace raw `<img>` with `PhotoFrame`.
- Widen the buffer from 2 to 3 spreads for smoother fast scrolling.
- Prefetch the next 2 spreads' images at low priority:

```js
useEffect(() => {
  upcomingSpreads.flatMap(getPhotoUrls).forEach(url => {
    const img = new Image();
    img.fetchPriority = 'low';
    img.src = url;
  });
}, [visibleRange]);
```

The virtualization already exists and works; this makes it invisible.

### Task 6 — Honest, specific progress copy

Wire [2.2](M2-2.2-sse-progress.md)'s real progress into copy that names the current work:

| Phase | Copy |
|---|---|
| Uploading | `Uploading photos — 18 of 25 batches` |
| Filtering | `Analysing quality — 612 of 1,000 · 418 kept` |
| Themes | `Choosing your three styles…` |
| Layout | `Designing variation 2 of 3 — spread 14 of 40` |
| Finalising | `Almost ready…` |

Specific counts read as competence; a generic spinner reads as a hang. Never show a spinner for more than 1 s without an accompanying number.

### Task 7 — Cross-fade route transitions

`upload → chat → generating → preview` are hard swaps today. Add a shared wrapper:

```css
.step-enter { opacity: 0; transform: translateY(8px); }
.step-enter-active {
  opacity: 1; transform: translateY(0);
  transition: opacity 240ms ease-out, transform 240ms ease-out;
}
@media (prefers-reduced-motion: reduce) {
  .step-enter, .step-enter-active { transition: none; transform: none; }
}
```

`opacity` and `transform` only — both are GPU-composited and skip layout and paint. Animating `height`, `top`, or `width` forces reflow on every frame and produces exactly the jank this stage removes.

## 6. Test plan

**Visual / performance**
- Cumulative Layout Shift = **0** on the carousel and spread viewer (Lighthouse).
- No spinner without a number visible for > 1 s.
- Photo grid paints < 100 ms after downsampling (local blobs, no network).
- Cross-fades hold 60 fps in the Performance panel.

**Component**
- `PhotoFrame` renders the gradient before load and the image after.
- Missing `dominantColors` falls back to the neutral skeleton.
- `aspectRatio` reserves correct height at several ratios.

**Functional**
- Reconciliation: a photo rejected by the server dims in place — it does not disappear and reappear.
- Object URLs are revoked after the server URL takes over — memory returns to baseline.
- `prefers-reduced-motion` disables transitions.

## 8. Risks & rollback

| Risk | Mitigation |
|---|---|
| Optimistic UI desyncs from server truth | `photo_id` is the join key and is client-minted; reconciliation is a dict lookup. Server state always wins on conflict. |
| Revoking URLs too early breaks images | Revoke only after the server URL is in `serverPhotos` and rendering. Verify with a slow-3G throttle. |
| Showing rejections upsets users | Frame it as curation, not deletion — `418 kept` is the headline, dimming is secondary. This is the product's core value made visible. |
| Skeleton colours clash with the real photo | Dominant colours come from the photo itself, so they match by construction. |
| Prefetch wastes bandwidth | Only 2 spreads ahead, `fetchPriority: 'low'`, and thumbnails are ~30 KB. |

**Rollback:** each task is independent. `PhotoFrame` can be reverted to plain `<img>` per call site; optimistic previews can be disabled by rendering from `serverPhotos` only.
